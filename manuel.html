Prérequis et environnement
Matériel, système d'exploitation et conteneurisation

Vérifier l'infrastructure avant déploiement

L'inférence locale repose sur l'adéquation entre les capacités de calcul et la taille du modèle. Une sous-estimation du matériel provoque un échec structurel de l'inférence ou un basculement sur le CPU avec une chute de performance de 100 tokens/s à moins de 5 tokens/s.

  • Ordinateur portable (Apple Silicon M1-M4, 16-32 Go RAM) : modèles 7B à 13B, exploitation de la mémoire unifiée et du Neural Engine.
  • Station de travail GPU (NVIDIA RTX 4090, 24 Go VRAM) : modèles 13B à 33B, idéal pour le codage agentique.
  • Serveur / Multi-GPU (2x RTX 3090/4090, 48 Go+ VRAM) : modèles 70B+, indispensable pour le raisonnement complexe et les fenêtres de contexte étendues.
  • Système d'exploitation : Linux (Ubuntu 24.04 LTS recommandé), macOS ou Windows.
  • Conteneurisation : Docker avec NVIDIA Container Toolkit pour la portabilité en production.
# Vérification Docker et NVIDIA docker --version docker run --gpus all nvidia/cuda:12.2.0-base-ubuntu22.04 nvidia-smi
2
Installation d'Ollama
Moteur d'inférence locale (port 11434)

Déployer le moteur d'inférence locale

Ollama est l'infrastructure de référence pour l'inférence locale. Il permet d'injecter des LLM locaux dans n'importe quelle stack logicielle par simple changement d'endpoint. Version stable : v0.33.2.

  • Linux (Ubuntu 24.04 LTS) : installation via binaire unique, géré nativement par systemd.
  • macOS & Windows : installation via paquets natifs, avec support automatique du GPU et du Neural Engine.
  • Docker : utilisation de l'image ollama/ollama, intégration avec le NVIDIA Container Toolkit.
# Linux - Installation via binaire unique curl -fsSL https://ollama.com/install.sh | sh # Vérification du service systemctl status ollama # Test de l'endpoint local curl http://127.0.0.1:11434/api/tags

Ollama expose une API compatible OpenAI sur le port 11434.

3
Téléchargement du modèle
Quantification GGUF Q4_K_M et chargement en VRAM

Sélectionner et charger un modèle quantifié

La réduction de l'empreinte mémoire sans sacrifier la précision sémantique s'effectue par quantification au format GGUF via le moteur llama.cpp. Le Q4_K_M est le standard industriel pour l'équilibre performance/ressources.

# Exemple sur une configuration RTX 4090 pour un modèle Llama 3.1 8B # FP16 : 14 Go VRAM, ~15 tok/s, 100 % précision # Q8_0 : 9 Go VRAM, ~28 tok/s, ~99 % précision # Q4_K_M: 6 Go VRAM, 95-110 tok/s, ~95 % précision (standard) ollama pull llama3.1:8b ollama run llama3.1:8b
  • FP16 (non quantifié) : 14 Go VRAM, ~15 tok/s, 100 % précision.
  • Q8_0 (8 bits) : 9 Go VRAM, ~28 tok/s, ~99 % précision.
  • Q4_K_M (4 bits — standard) : 6 Go VRAM, 95-110 tok/s, ~95 % précision.

Le modèle doit rester résident en VRAM pour éviter les collisions mémoire.

4
Déploiement de Hermes Agent
Runtime d'agent autonome (Nous Research)

Installer le démon système d'arrière-plan

Hermes Agent s'exécute en tant que démon système d'arrière-plan et expose une interface API HTTP compatible avec les standards de l'industrie (par défaut sur le port 8642).

  • Hébergement recommandé : Serveur Virtuel Privé (VPS) ou infrastructure cloud conteneurisée sous Docker, confinant l'agent dans un bac à sable isolé.
  • Port d'écoute : 8642, activé via API_SERVER_ENABLED=true.
  • Sécurité : authentification Bearer via API_SERVER_KEY.
  • Déploiement Docker : image ollama/ollama avec NVIDIA Container Toolkit pour la portabilité en production.
# Docker - Lancement d'Hermes Agent docker run -d \ --name hermes-agent \ --gpus all \ -p 8642:8642 \ -e API_SERVER_ENABLED=true \ -e API_SERVER_KEY=votre_cle_secrete \ -v hermes_data:/app/data \ nousresearch/hermes-agent:latest

Hermes Agent expose trois points d'accès API distincts.

5
Configuration du serveur API
Endpoints, clés d'authentification et variables d'environnement

Configurer les points d'accès et les garde-fous

L'architecture API d'Hermes s'articule autour de trois points d'accès aux caractéristiques sémantiques distinctes.

Endpoint Type Usage
POST /v1/chat/completions Stateless Format OpenAI Chat Completions, flux SSE avec keepalive toutes les 10 secondes.
POST /v1/responses Stateful Gestion d'état via previous_response_id ou conversation.
POST /v1/runs Asynchrone Soumission de requêtes longues, retourne un run_id.
# Fichier de configuration YAML (exemple) gateway: api_server: enabled: true port: 8642 history_tool_output_max_chars: 2000
  • Idempotency-Key : 1 à 255 caractères ASCII visibles, réserve le run_id pendant 24 heures.
  • Keepalive SSE : ligne de commentaire : keepalive toutes les 10 secondes pour éviter les timeouts.
  • Clé d'authentification : transmise via header Bearer API_SERVER_KEY.

Trois endpoints API : chat/completions, responses et runs.

6
Variables d'environnement critiques
Stabilité multi-utilisateurs et gestion des ressources

Configurer l'exécution en production

Pour garantir la stabilité en environnement multi-utilisateurs, l'expert doit configurer les variables d'environnement suivantes.

# Variables Ollama critiques export OLLAMA_FLASH_ATTENTION=1 # Active les optimisations de calcul export OLLAMA_NUM_PARALLEL=4 # Nombre de requêtes traitées simultanément export OLLAMA_MAX_LOADED_MODELS=2 # Limite le nombre de modèles résidents en VRAM # Variables Hermes Agent export API_SERVER_ENABLED=true export API_SERVER_KEY=cle_robuste_256_caracteres export OLLAMA_HOST=http://127.0.0.1:11434
  • OLLAMA_FLASH_ATTENTION=1 : active les optimisations de calcul pour un gain de vitesse immédiat.
  • OLLAMA_NUM_PARALLEL : définit le nombre de requêtes traitées simultanément.
  • OLLAMA_MAX_LOADED_MODELS : limite le nombre de modèles résidents en VRAM pour éviter les collisions mémoire.

Ces variables évitent la saturation de la fenêtre de contexte et de la base response_store.db.

7
Cloisonnement et plafonnement des sorties
X-Hermes-Session-Key et history_tool_output_max_chars

Sécuriser la mémoire et limiter la consommation de tokens

Le risque majeur d'explosion des coûts découle de la taille des données spatiales renvoyées par les outils. Une seule requête SQL/Spatial renvoyant des entités GeoJSON complexes peut générer plusieurs mégaoctets de texte.

  • X-Hermes-Session-Key : identifiant stable de l'utilisateur ou du canal (ex: agent:gis:webui:user-88, max 256 caractères, rejet des caractères de contrôle). Définit la portée de mémoire appliquée et garantit le cloisonnement strict des mémoires multi-utilisateurs.
  • history_tool_output_max_chars: 2000 : plafonne les sorties d'outils stockées dans l'historique. Le tronquage conserve le début de la réponse suivi de la mention ...N more chars.
# Header HTTP pour cloisonnement des sessions X-Hermes-Session-Key: agent:gis:webui:user-88 # Plafond dans le fichier de configuration history_tool_output_max_chars: 2000

Cloisonnement par clé de session et troncation des sorties d'outils à 2 000 caractères.

8
Vérification, test et mise en production
Test des endpoints et intégration QGIS / GeoAI Assistant

Valider le fonctionnement de l'infrastructure

Une fois le déploiement terminé, vérifier que l'API répond correctement et que l'inférence locale fonctionne avant d'intégrer un client tel que le plugin GeoAI Assistant dans QGIS.

# Test de l'endpoint chat (stateless) curl -X POST http://localhost:8642/v1/chat/completions \ -H "Content-Type: application/json" \ -H "Authorization: Bearer cle_robuste_256_caracteres" \ -d '{ "model": "gemma:12b", "messages": [{"role": "user", "content": "Bonjour, vérifiez que l\'inférence locale fonctionne."}], "stream": false }' # Test de l'endpoint runs (asynchrone) curl -X POST http://localhost:8642/v1/runs \ -H "Content-Type: application/json" \ -H "Authorization: Bearer cle_robuste_256_caracteres" \ -d '{"prompt": "Analyser l\'emprise de Saint-Lô", "idempotency_key": "cle_unique_24h"}'
  • Intégration QGIS : le plugin GeoAI Assistant s'appuie sur cette infrastructure (Gemma 12B, module RAG, couche d'outils PyQGIS/GDAL/PostGIS).
  • Annexe 1 : architecture Multi-AI avec Gemma 4B (rapide), EmbeddingGemma (recherche), Gemma-Geo (spécialisé) et outils Python/PyQGIS.
  • Annexe 2 : pseudo-flux d'orchestration — recevoir la demande, normaliser, rechercher la documentation, générer un plan, valider, exécuter, journaliser, restituer.
  • Gouvernance : validation déterministe des commandes avant exécution, files d'approbation humaine via /v1/runs/{run_id}/approval.

L'infrastructure est opérationnelle après validation des trois endpoints API.
